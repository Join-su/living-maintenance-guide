# llmopsagent-deploy — 개발 규칙

Deployment Server(Pack 버전 하나 = 서버 하나) 저장소. 브랜치 dev, 로컬 커밋만.

## 지키고 있는 규칙

- 새 설치 · push · 실제 provider 호출 · 실제 임베딩 API 호출은 지시 · 승인 때만 한다(전용 `.venv`는 지시 008 승인 범위 안에서만).
- 비밀 값(배포단 `.env`, DSN · 비밀번호)은 출력 · 기록 · 커밋하지 않는다. 설정에는 환경 변수 이름만 둔다.
- `llmops-lite-v2` · `task10-pack` 저장소에는 쓰지 않는다(읽기 · `git archive`만). 등록 줄은 승인 때 llmops `deploy-bootstrap`으로만 더한다. packrt · 공유 기록기 코드는 고치지 않는다.
- 개발은 VFE(vibe-factory-evolution)로 한다. 관찰 기준선은 EV-001이고, 지금 기준은 최근 승격된 Product Contract Snapshot(`.vibe-factory/evolutions/*/snapshot/`, 로컬 작업 기록 — 기록 전용 로컬 git, 규칙 02)이다.

## 기존 흐름 · 확장 지점 원칙 (2026-10-13 사용자 결정)

- 이 제품의 승인된 흐름(VCF Use Case · Prototype Bundle, 또는 관찰 기준선)과 그것이 진화한 VFE 기준선(제품 · UI 스냅샷)은 **지켜야 할 약속**이다. VFE가 새 번들을 만들어도 "원래 흐름을 유지한다"는 뜻은 이어진다.
- 새 기능은 **기존 흐름이 마련해 둔 확장 지점 위에 얹는다.** 같은 역할의 새 객체 · 표 · 화면 · 경로를 따로 만들지 않는다. 새로 만들어야 한다면 기존 것으로 안 되는 이유를 VFE 영향 지도에 적는다.
- VFE E1 영향 지도에서 새 기능마다 **그것을 담을 수 있는 기존 흐름 · 객체 · 화면을 먼저 찾아** 적는다.
- 기준선 약속을 바꾸는 변경(예: "비교는 비교 화면에서만")은 **"약속 변경"으로 표시하고 질문으로 올린다.** 지시나 설계 문서가 그렇게 하라고 해도 먼저 묻는다.
- 지시 · 설계 문서가 기존 흐름과 겹치거나 부딪히는 것을 발견하면 **따르기 전에 질문으로 올린다.** 지시보다 기준선 확인이 먼저다.
- 완료 확인은 **사용자 흐름을 기존 화면(또는 기존 사용 경로) 위에서 한 바퀴 도는 것**으로 한다. API · 요소 단위 시험만으로 완료라고 하지 않는다.
- 근거: 2026-10-13 제품 흐름 이탈 사건(오케 조사 INV-01) — 별도 후보 표 · 비교 화면 · 승인이 기존 release · 비교 · 판정 흐름 밖에 만들어짐.

이 저장소의 확장 지점 예(Product Contract Snapshot EV-004 기준):
- 새 배포 = `config/`의 설정 파일 하나(S-07). `v0-pg-local` · `v1-pg-local`처럼 서버 경로(`POST /runs`, S-01)는 그대로 쓴다.
- 등록은 llmops.db `deployment` 표(`deploy-bootstrap`, S-06), 실행 기록은 공유 `TraceWriter` → PostgreSQL `trace`(S-05)에 얹는다. 배포단 자체 등록 표 · 기록 표를 따로 만들지 않는다.
